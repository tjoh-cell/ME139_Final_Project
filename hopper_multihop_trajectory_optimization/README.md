# 2D Hybrid Hopper — Multi-Hop Trajectory Optimization (Standalone Version)

**This is a separate project.** The original `hopper_2d.py`, `run_mpc.py`, `hybrid_hopper.py`, and `run_multi_hop.py` in your earlier project folders are not changed. This new folder includes a self-contained copy of the previous hybrid dynamics to make runs reproducible.

## Quick start

Python 3.10+. In a terminal opened inside this folder:

```bash
python -m pip install -r requirements.txt

# Compact baseline example (original passive-spring parameters)
python run_optimized_hops.py --target 0.45 --lookahead 3 --maxfev 50

# Your modified parameters from the screenshots: 1 m leg, 450 N/m spring,
# 1 kg body, 16 N*m torque, 0.5 m preload, 0.65 rad max reference.
python run_optimized_hops.py --scenario aggressive --target 10 --compression 0.5 --lookahead 3 --maxfev 35

# Fast smoke tests
python -m unittest test_optimized.py test_hybrid.py -v
```

The program writes `results_optimized/multi_hop_plots.png`, `multi_hop.gif`, `trajectory.csv`, `summary.txt`, and **`optimization.json`**. The JSON lists each optimization horizon, its best jointly optimized reference angles, predicted terminal landing, cost, and whether its simulation completed.

To animate a saved CSV without solving again:

```bash
python animate_csv.py --csv results_optimized/trajectory.csv --target 10
```

## How the controller has changed

The previous `plan_tilt_one_hop()` optimized only **one stance body-angle target**, aiming at a limited local waypoint. The new function `optimize_horizons()` compares **different independently optimized sequence lengths** (by default, N=1,2,3).

For each candidate N it jointly chooses **N separate stance body-angle references**, not one angle reused every hop:

```
Decision vector for N=1: [alpha_ref_1]
Decision vector for N=2: [alpha_ref_1, alpha_ref_2]
Decision vector for N=3: [alpha_ref_1, alpha_ref_2, alpha_ref_3]
```

Each candidate is simulated through *every* required stance, flight, and impact reset. Its objective is:

```
J_N = 100*(foot_x_at_end_of_sequence - target)^2
    + hop_cost*N
    + tilt_cost*sum(alpha_ref_i^2)
    + friction_cost*sum(touchdown_friction_shortfall_i^2)
```

The optimizer is allowed to choose **negative angles** after the foot overshoots. Crucially, intermediate hops are **not constrained to move closer to the goal**, so a short backwards hop can precede a longer forward one, or a backwards correction can follow an overshoot.

Among completed/feasible *simulation sequences*, it chooses the horizon with the smallest objective. It then executes the first predicted hop, receives the new touchdown state, and normally reoptimizes. `--execute-plan` instead executes the previously chosen sequence before replanning. Different numbers of hops are compared on each replan; `--safety-max-hops` is merely a safety cap, not a requested hop count.

> **Optimizer distinction:** This is **multi-hop hybrid shooting optimization** over attitude references using SciPy's bounded derivative-free Powell method, not a single CasADi/IPOPT NLP optimizing the instantaneous torque at every step. The reaction-wheel torque is generated by the existing contact-limited stance PD controller and flight PD controller. Since impacts and event detections make the objective nonsmooth, this is a useful intermediate design before an explicit multiphase CasADi direct-transcription method. The result is a *local* optimum, not a proof of global optimality.

## Stopping condition — you do NOT need zero energy

The simulation ends when the first of these occurs:

1. The touchdown foot lands within `--tolerance` of the target (default 0.05 m).
2. The touchdown foot has crossed from one side of the goal to the other `--stop-after-crossings` times (default **2**, roughly an over-and-back correction).
3. No candidate N-hop trajectory completed; the stance/flight becomes invalid.
4. The emergency `--safety-max-hops` cap (default 8) is reached.

The simulator stops producing additional hops even though the physical robot would **not** stop moving when it still has energy. A goal crossing is detected between **consecutive touchdown foot x-positions**, not within each continuous flight path. No particular physical energy threshold is imposed. See `goal_crossings` and `status` in the report.

## Physics retained from previous hybrid simulator

- Stance `[alpha, phi, l, alpha_dot, phi_dot, l_dot]`: pin foot in place, compress and release unilateral damped spring, flywheel reaction torque, stance friction/normal-force torque projection.
- Flight `[x, z, vx, vz, alpha, phi, alpha_dot, phi_dot]`: ballistic COM translation with reaction-wheel attitude dynamics; no thrusters.
- Touchdown: at foot height `z - l0*cos(alpha) = 0` while descending, apply a **massless point-foot sticking velocity projection** onto stance; spring then compresses, rebounds, and triggers takeoff at unloaded leg length while extending.
- Initial spring preload supplies the first hop. Subsequent hops may lose energy to damper and impact. The motor can exchange mechanical energy with the body/wheel.

## Examples observed during validation

A baseline test at goal +0.45 m compared 1-, 2-, and 3-hop candidates and selected a 2-hop solution, landing near +0.450 m. An aggressive test at goal +10 m and initial compression 0.5 m selected 3 hops, landing approximately at -0.176 m, +2.652 m, then +10.000 m. The optimizer sometimes makes an initial backward hop when its multihop objective favors that sequence.

A targeted reversal test was also run: after a manually forced forward hop landed at +0.127 m with a goal of +0.080 m, the optimizer selected a negative next-hop reference (approximately -0.208 rad) and predicted a landing near +0.080 m. Another tested 2-hop reference sequence crossed the goal twice.

These results depend on the perfect simulation model and optimization settings. They should **not** be interpreted as physical hardware feasibility.

## Engineering limitations: read before hardware selection

1. **The sticking touchdown model does not enforce a Coulomb friction cone on the impact impulse**. Each rollout reports a friction shortfall. The objective penalizes it **softly**, but an accepted plan may still require impossible sticking contact. This is the first physics issue to fix before comparing hardware designs. A finite-time compliant/slipping foot or physically feasible contact impulse law is the next priority.
2. **Motor speed limits in the inherited controller are applied to flywheel's inertial angular speed**, while the physical motor rotor speed normally corresponds to flywheel speed relative to the body. `run_optimized_hops.py` now reports peak `abs(phi_dot - alpha_dot)` and absolute mechanical motor power demand for diagnostic purposes. Do not use the simple torque clamp to choose a motor yet; add torque-speed/power/thermal constraints first.
3. **No hardware layout, foot mass, leg swing/deployment, actuator losses, imperfect state feedback, or motor electrical dynamics**. In particular, the leg is kept at its unloaded length in flight.
4. **No guarantee of global optimization or near-goal stabilization**; Powell is a local derivative-free solver, with limited function evaluations. Different seeds, lookahead, and control law can give different results.
5. A physical robot with remaining energy would continue hopping even if this simulator *stops displaying* motion at the goal or after two crossings. The stop is a **planning/visualization endpoint**, not a physical braking actuator.
6. This solver can choose unnatural backwards-first sequences. To discourage them you could add a cost on initial progress or total traveled distance, but for now this is intentionally allowed to demonstrate long-horizon reasoning.

## Source files

- `hybrid_hopper.py`: a copied, unchanged version of previous stance/flight/impact physics and PD torque law.
- `trajectory_planner.py`: **new** N-hop candidate rollouts, cost and bounded optimizations, receding planner, overshoot crossing counter.
- `run_optimized_hops.py`: new CLI and JSON reporting; reuses visualization from `legacy_run_multi_hop.py`.
- `legacy_run_multi_hop.py`: copy of the old plotting/animation and one-hop CLI (not used as the planner).
- `animate_csv.py`: standalone GIF-from-CSV script for previously saved runs.
- `test_optimized.py`: tests for multi-horizon plans, different angles, backward correction, nonzero-energy stopping.
- `test_hybrid.py`: original contact and passive-energy tests.

This project is intentionally not a final hardware-grade robot dynamics simulator. It is a reproducible stepping stone from greedy one-hop control to multi-hop optimization.
